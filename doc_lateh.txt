\section{Introduction}
A FIR filter (Finite Impulse Response filter) is a filter whose output depends only on a finite number of current and past input samples. It is described by:

\[
y[n] = \sum_{k=0}^{N-1} h[k] \, x[n-k]
\]

where:

\begin{itemize}
    \item $x[n]$ is the input signal,
    \item $y[n]$ is the output signal,
    \item $h[k]$ are the filter coefficients (taps)
\end{itemize}

Each input sample is multiplied by a coefficient and the products are summed together. In hardware, FIR filters are typically implemented using a chain of multipliers, adders, and delay registers.\par
\vspace{0.2cm}
Self-Purging Redundancy (SPR) is a fault-tolerance technique that employs multiple redundant instances of a module and automatically excludes faulty instances from the final decision process. The operation of SPR can be summarized as follows:

\begin{enumerate}
    \item Replicate the module $M$ times.
    \item Apply the same input to all replicas.
    \item Compare the outputs of all replicas.
    \item Identify modules whose outputs agree with the majority.
    \item Exclude modules whose outputs deviate beyond a predefined tolerance threshold.
    \item Generate the final output using only the trusted replicas.
\end{enumerate}

Here we apply SPR on the FIR filter at the MAC module level - each "tap" has M redundant MAC modules whose outputs are fed to a voter.

\section{Architecture}

The designed Self-purging FIR filter was written to be fully parametrized. This means that the input data width, filter order and number of redundant MAC modules can be changed through the constants set in the top module of the project.\par
\vspace{0.2cm}
Since both the MAC modules and the voter have several pipeline stages, the multiplication inputs for each successive Self-purging MAC module within the filter need to be delayed by the number of pipeline phases present in both the MAC modules and the voter (Figure 2).\par

The implementation of the shift registers is trivial and what we can note is that we use an enable signal to stall the whole filter when the data input is not valid. This signal is visible on Figure 3 for the shift registers as well.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\linewidth]{ShiftReg.png}
    \caption{Shift register implementation}
    \label{fig:placeholder}
\end{figure}

The MAC modules are straight forward, a multiply and accumulate operation with a pipeline installed to improve throughput (Figure 4). The outputs are fed to a voter (Figure 5) which compares each input with each other using XOR gates. The tolerance of the comparison can be adjusted by changing the number of bits which are compared. This comparison along with the current values of the inputs determines the switch enable signals and voted output.

\section{Testing results}

Running a simulation of the filter for three redundant modules and three "taps" or three coefficients gives us the waveforms shown in Figure 6. The green colored signals are the inputs and outputs of the filter while the yellow, blue, and pink colored signals are, respectively, the inputs and outputs of Self-purging MAC modules. We can clearly see that for each MAC (or for each of the colors) the results are shifted by the number of pipelines we have per MAC module.\par
\vspace{0.5cm}
If we were to look at the first valid input into the filter we can see that it's corresponding output appears twelve clocks later. This number corresponds to the product of the number of "taps" and the number of pipelines that we have within one self-purging MAC module.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\linewidth]{tbResult.png}
    \caption{Simulation of filter}
    \label{fig:placeholder}
\end{figure}

To simulate a stuck-at fault in the system we use the tcl command:
\begin{lstlisting}[language=tcl]
restart
add_force {'signal_path'} -radix hex {0000}
run all
\end{lstlisting}

While to undo the effect of the set stuck-at fault previously applied we use the tcl command:
\begin{lstlisting}[language=tcl]
remove_force {'signal_path'}
\end{lstlisting}

We expect to see the same output chosen when there is no fault (Figure 7) as well as when there is a single stuck-at fault (Figure 8). The difference in those two cases would be the switch enable signal, which should disable the MAC with the stuck-at fault. If we had two stuck-at faults and three redundant modules the output voted should be the erroneous one and that will also be reflected in the switch enable signals, which will disable all three MAC modules (Figure 9).

\section{Timing and resource analysis}

The inputs to the program include the neural network topology and dimensions, the paths to the training and test datasets, and the number of processes or threads used for execution. In our experiments, we vary the network size and the number of execution threads to examine their effect on training time. The primary objectives are to demonstrate that parallel implementations achieve measurable speedup when the neural network is "sufficiently large", and that this speedup decreases as the network size becomes smaller. We will also show that the change in network size doesn't have a decisive impact on network precision.\par

The speed-up results marked in the table with an asterisk for the 8 thread version of the program are smaller than the results we have for the 4 thread version. The explanation for that could be the hardware limitation. The program is run on an intel i7 10th generation processor which possesses 8 threads in total. Using all of them could be influencing the result as this program isn't the only process running on the processor. This idea could be supported by the results we get when using 6 or 7 threads, making sure to use layer dimensions that are divisible by one of the two numbers as well as by four and eight so that the load is balanced (see table 5 bellow).\par
